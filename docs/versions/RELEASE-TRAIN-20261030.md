## 版本与分支：按现有 Skills 的最小方案

依据用户的 [git-workflow](https://github.com/CHNISam/agent-skills/blob/master/git-workflow/SKILL.md)、[release-please](https://github.com/CHNISam/agent-skills/blob/master/release-please/SKILL.md) 与 [0.x 迁移规范](https://github.com/CHNISam/agent-skills/blob/master/release-please/references/pre-1-and-migration.md)：**项目现有分支约定优先，按真实发布批次升版，Release Please 仅用于生成待批准版本提案，不自动发布。** 现有 `.github/workflows/release-proposal.yml` 也仅可手动在 develop 发起提案，`skip-github-release: true`。

| 阶段 | Git 分支 | 项目源码版本 | 千星平台实际行为 |
| --- | --- | --- | --- |
| Alpha 收敛 | `develop` | **现有 `0.11.0`**（尚未 Tag / 发布） | 保留旧 Alpha 作品与数据 |
| **Beta 测试** | **`release/1.0.0`**（从已稳定的 develop 切出） | **沿用 `0.11.0` 候选，不额外制造预发布版本号**；用确切 SHA、buildId、GIL hash 识别不同 Beta 构建 | 创建独立奇域存档并导入、测试；如走先行体验，使用官方真实发布状态和允许的数字版本、按用户确认的首次报名流程操作 |
| **正式首发** | **`master`**（release 验收后经 PR 合入，修复回合 develop） | **`1.0.0`**，验证后在正式提交创建不可变 `v1.0.0` Tag | 同一作品按平台正式发布 / 大版本流程升级；核对平台实际数字版本与发布回执 |
| 后续 M4 | `develop`，按需短命 `release/*` / `hotfix/*` | **有实际修复或功能批次才**考虑 `1.0.1` / `1.1.0` | 每次按真实 UI 更新版本和状态、保留证据 |

**不要混淆**：`release/1.0.0` 是 Git 分支名，不是千星平台版本；`Beta` 是测试/发布阶段，不强制对应 `1.0.0-beta.1`；不额外增加以 `RC` 命名的版本号或分支；但仓库 M5 要求的同一冻结候选验收必须保留。SemVer 确实允许 `1.0.0-beta.1`，但本项目与当前官方界面没有必须采用它的需求，故**本发布列车不采用**。原先擅自建议的 `0.12.0-beta.1` 和 `1.0.0-beta.1` 在此撤回。

**正式发布前核对**：千星平台版本号若自动生成或只有数字选项，以官方当次实际三段数字、升级选项为准，不把内部 Git 标签填入平台版本栏；尤其正式大版本不能猜测。若无法手动选择成 `1.0.0`，保留平台原始版本号并单独记录，不虚构等同关系。发布状态（先行体验/正式）与平台数字版本是两回事，是否允许转正式、比赛是否有效须留真实回执。每次发布记录作品 GUID、平台显示版号、源码 SHA、GIL hash、发布状态和时间。原 14 个历史开发 Tag 保留，不打假 Tag。

**最简发布动作**：M3 收口与集成 CI 通过 → 从稳定 develop 创建 `release/1.0.0` → 用该分支产物测试 Beta → 仅修阻断项 → M3 可玩性通过 → 将正式版本升至 `1.0.0` 并重建最终冻结候选 → 对这个准确 SHA/buildId/GIL hash 完成 M5、官方负载、UI 与设备验收 → 该已验源码经 PR 进入 master 并回合 develop → 人工平台发布、记录凭证。验收后任何影响版本、生成物或 payloadDigest 的改动均须重建并重验，不能复用旧 `0.11.0` 候选证据。未来 M4 逐批迭代。不要为了流程而多开分支、逐轮升版本或开发新发布系统；M5 同一冻结候选的验收标准保持不变。

本 PR 只记录方案，不创建 release 分支、不修改 package/lock/manifest/游戏显示、不 Tag、不发布。
