## 1.1 OpenDesign 实测结案：完整环境未扭转视觉结果

**实验目标：** 《杀戮原塔2》爬塔路线地图页的原创游戏 UI / UX、美术构图和可交互高保真原型；不是测试普通网页能否生成 HTML，也不是验证千星奇域原生运行。

| 实验组 | 环境 / 模型（按 Owner 描述） | 实际观察与解释 |
| --- | --- | --- |
| A | Dot + OpenDesign 的部分 Skills，未搭建完整 OpenDesign | 视觉效果不佳；作为非完整环境基线，不代表全部 OpenDesign 能力 |
| B | OpenDesign 桌面完整工作流 + Codex CLI + GPT-6 Luna | Owner 对实际原型视觉结果评价很差；不满足项目主设计质量要求 |
| C | 同一 OpenDesign 工作流 + GPT-6.1 Sol / Medium 等后续配置 | Owner 复试后仍判断不达标，部分成品甚至逊于 A；增加环境和推理配置未带来可用的原创审美提升 |
| 排除项 | 有一次请求沿用「只能交付 Figma Make」的旧约束，Agent 因无 Figma Make 操作入口而终止 | **这是任务环境/交付约束失败，不计作视觉品质样本**；不与 B/C 混为一谈 |

**Owner 最终决策（2026-11-02）：OpenDesign 在本项目当前需求下 No-Go，终止投入。** 不再通过切换 GPT Medium/其他推理档、堆叠 Skills、重装设计壳来继续这一轮。决定由实际使用价值不足触发，不要求补齐账单或截图才能停止；但因缺少原始截图、逐轮版本/日志及严格盲评，**不得将其扩写成模型通用能力排名或量化性能结论**。

**经验沉淀：** 当前瓶颈是能主导游戏美术风格、构图与交互品质的设计模型，而不是缺少 HTML 预览壳。Skills / 可视预览有助于实施和评审，但不能替代原创设计判断。GPT/Codex 仍承担工程实现、已有设计还原与验证；主设计模型另行筛选。未来只有出现**可比较的真实游戏 UI 样品与明确质量/成本优势**，才考虑复核这条已淘汰路线；无须为 OpenDesign 建立独立重试任务。

## 2. Magic Patterns：成本线索与尚未解决的问题

本轮讨论引用的 Starter **约 $20/月、1000 Credits** 及产品方曾提供的 **Opus 5.5 历史项目**消耗示例：

| 示例工作量 | 示例 Credits | 解释 |
| --- | ---: | --- |
| 首次生成 | 约 70 | 1000/70 ≈ **14 次首稿**，只是算术示例；**不是每月最多 14 条消息** |
| 小型原型，约 4–10 版 | 110–200 | 可能包含多轮修改 |
| 完整页面 / 流程，约 11–20 版 | 约 400 | 一个月大约只能承担少数深度任务 |
| 深度打磨，约 21–50 版 | 约 950 | 接近一个月的该档示例额度 |

上述数字是**产品历史示例和讨论时套餐口径，不是用户账号的实际账单，也不是所有模型的固定扣费标准**。产品曾改变 Credits 计费机制，旧年份的「一条消息花费多少」不能不经转换直接套用。尤其要避免以下错误：

- **不能**把 Opus 示例消耗直接当成 Sonnet、Gemini、Auto 等其他模式的消耗。
- **不能**拿 API 每百万 Token 单价直接换算平台 Credits：设计 Agent 可能有额外上下文、工具和隐藏编排。
- **目前缺少**同一战斗页、同等轮次与同等模型设置下 Magic Patterns 与 Figma Make / Claude 官方入口的可靠成本对照。
- 有社区用户抱怨付费 Credits 不耐用，但缺少足够完整、可审计的「1000 Credits 实际完成多少轮合格设计」账本；不写成已证实统计值。
- 若局部 Visual Edit / Fix 功能在当前套餐和版本确实不扣 Credits，需以账号内的实际 History 验证，不能假定所有修改免费。

## 3. 下一轮最小验证：Magic Patterns 战斗页

**目的：** 不扩大订阅开支，判定它能否以可接受成本输出具有游戏感且能精修的战斗页，不把网页原型直接当作千星奇域原生可交付件。

1. 使用固定的《杀戮原塔2》**战斗页任务说明**、统一桌面尺寸（建议 1280×720）、同组参考素材和交互状态；与 Figma Make 既有可接受样稿对照。明确记录提示词版本、模型是否可选及实际显示名、项目 / 资料是否真实加载；如果输入不同，仅称弱对照。
2. **三轮上限的最小测量：** A 首稿（整体构图、色彩与游戏感）；B 指定 1–2 处局部精修（检查是否破坏现有视觉）；C 指定卡牌选中 / 拖动、目标高亮、受击反馈之一的可操作状态（检查动效与可用性）。每轮保存产物 / 截图和 **Credits History 前后差值**；无免费额或需额外充值即停止，不自动付费。
3. 单独记录：总 Credits、每轮增量、模型与档位、是否有无扣费手动编辑、每轮是否得到用户接受的改进、最终可导出内容、响应式及组件状态。尽量对照统一设计评分，不用好看的静态图冒充动效成果。
4. 形成每个候选的 **质量 / 成本双指标**：用户认可的设计版本数、达到合格所需轮次和实际 Credits / 费用。先判定「首稿审美」与「可持续精修」是否同时成立，再讨论订阅。
5. **仅在本组产物和账单可复核后**，对 Magic Patterns 给出条件性 Go / No-Go；如果首次结果不如现有 Figma Make 且消耗很高，立即停止继续付费试错。

## 4. 与正式研发的隔离

- 现阶段结论：Figma Make 是**质量基准但额度不足**；Magic Patterns 是**优先保留的候选但成本未知**；**OpenDesign + 当前 GPT/Codex 组合与 Replit Design 本项目 No-Go**；其他入口仍按证据决定是否测试，不继续为排名购买订阅。
- 不以本记录推进 TASK-95 到 Done，不提前勾选任一 AC；现有 M4 非设计工程、修 Bug、已批准 UI 实现照常推进。
- 设计验证不自动授权上传整个仓库、购买套餐、安装插件或操作用户桌面；素材许可证、导出限制与正式集成仍逐项核实。
- HTML / React 原型需单独验证平台可表达性、控件 / 图元预算、真实 PC / 安卓性能，以及 Owner 对成品设计的批准。后续任何正式美术 / 动效改动依 TASK-95 的**对应方案有效结论**，不能用本阶段主观体验替代。

**当前缺证据清单：** Magic Patterns 实测 Preview 与截图、各轮 Credits History、模型显示名 / 套餐、相同条件下 Figma Make 对照资料、交互录像、游戏原生实现与实体设备证据。OpenDesign 历次原型与逐轮运行记录目前未归档，**不影响已作出的项目级 No-Go**，但不以此生成假定的打分。以上未提供即保持相应指标「待验证」。
