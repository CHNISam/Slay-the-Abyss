## 2. 补全四条原生 M7 工作线（先查重再用 CLI 建单）

**G1｜全库依赖环与领域所有权收敛**（候选归 TASK-74 的新子任务，或独立 M7 任务）

- **范围**：以最新源码生成全量即时/延迟依赖图、SCC 成员与内部边清单、按 `(domain, layer, role)` 标识职责。重点核查原有 104 成员大 SCC、RelicHooks 的 Session/Combat 混合职责、Combat/Run/Actor/CardActions/Nodes 边界；识别真实反向依赖而不是因双向业务调用就机械禁止。
- **实施**：逐条记录 `from → to → 引用位置 → 当前状态提交 owner → 移除/保留理由`，按 P0/P1 优先消除跨职责反向边；每片固定旧新 RNG、事件、队列、回滚、别名和失败轨迹；对已治理边界加含延迟加载的可执行防回退门禁。
- **验收**：最终 SCC 成员/内部边绝对值与基线同算法对比；大 SCC 必须有实质收敛，**不得先拍脑袋设 104→80 为结项数字**：按最新完整图区分即时加载环、合法延迟边、跨域非法方向；将 104 成员大 SCC 的每类关键边、状态所有权和可被证明的真实解环路径审全，消除全部已确证的 P0/P1 反向依赖；被保留的边必须有行为/生命周期证据、责任归属和防新环门禁。最终 SCC 绝对值和原因必须公布，未经证实的残余不能随意标成 P2 或因数字下降就验收。未达并未经 Owner 接受时不得收口。

**G2｜全库高复杂度与超大模块治理**（候选归 TASK-74 的新子任务）

- **范围**：全函数/匿名回调/初始化块持续同源量化，包含最大 CC、CC>15 / >30、最长函数、>1000行文件；优先 Combat、Actor、MapUI、CardActions 与剩余高风险入口。
- **实施**：按真正职责/状态边界治理，先固定完整旧新行为，再拆分；新增 helper 一律计入原门禁，不把复杂逻辑搬到 helper、测试或生成脚本骗指标。
- **验收**：当前最高风险调用链无未治理 CC>30；所有新治理职责函数仍遵守 CC≤15；将 **67 个 CC>30、最大 CC75、超千行 Combat 文件**列出文件/函数、测试风险、职责和真实变更频次；先治理会阻碍 M8 角色/内容迭代的 P0/P1 热点，要求其 CC≤15 或以完整旧新行为及明确分层接口证明安全；新职责全部受硬门禁。对其余热点给出书面 Owner 签署的风险可接受范围及后续非阻塞安排，不能仅以『显著下降』等无阈值词结项，也不能将所有 258 个 CC>15 同权分配无限期清零。最终绝对目标在首份完整机器清单审查后写入原生 AC。

**G3｜端到端运行时技术性能基准与优化**（M7 工程工作线；M8 设备体验继续独立验收）

- **范围**：代表性冷启动/二次启动、开局/战斗/回合结算、地图/菜单/奖励切换，覆盖 Lua 模块导入、Host/UI 原生 setter、snapshot 复制、核心事务、内存及重入/销毁热点。核查旧工作单对重复 render、稳定牌几何写入、药水拖动查询的承诺是否真的实现并保持。
- **验收**：相同代码身份、输入、种子与可复现 Host/官方候选条件下，记录至少 3 组有解释力的前后配对样本、总耗时及 P50/P95、内存与原生写入次数；对原静止 300 帧重复提交等目标给出绝对数量。不能只测快的子模块，整条主要路径不得出现无解释回退；首次真实设备证据若没有，明确交接 M8 的 TASK-4.21，**不得宣称游戏实机性能良好**。涉及设备结项的 AC 保持 UNVERIFIED，不在 M7 技术模型里伪造。

**G4｜仓库体积、LFS、冷构建/检出成本与 Agent 导航**（候选新 M7 任务，复用已有 CI/导航工作）

- **验收**：同环境前后列出 Git checkout/下载字节、LFS、冷构建墙钟及其预算/收益；消除**已证实**的重复下载与无用派生物，或以来源实测证明不值得处理；不重写 Git 历史、不删合法 fixture、不可再生资源不误删除，跨平台构建/License/官方候选一致。关键无成本数据时不得标为「轻量化已完成」；Agent 导航只改已证实的使用阻塞，复用 TASK-87，不另建重复指引系统。
