# 战后奖励叠字的根因与回归守卫

2026-10-24，基线 `b91a461`（PR182）。复用 TASK-52 的奖励流程修复及 TASK-4.5 的界面品质责任；此附件不修改任务状态或实机验收项。

## 已确证的问题

用户实机看到选牌后「卡牌已加入牌组；其他奖励请单独处理。」与「战斗奖励」叠在一起。离线重现使用 `buildUI()` 生成实际导入控件树，再通过现有真实宿主夹具运行 `Run.finishCombat`、选牌、跳过、领取药水、满槽拒绝及取回失金。除把敌人设为已死亡以隔离战后边界之外，没有伪造奖励文本或卡牌事务。

`abyss_battle_ui` 的这些回调把结果写进共享 `notice`；`render()` 又保持 `rewardStage` 显示，并把它的标题改为「战斗奖励」。共享提示没有切换页面所有权，也没有避开奖励标题区域。实际渲染后的两个文本框是：

| 文本 | 中心 x/y | 宽/高 | 纵向范围 |
|---|---|---|---|
| `rewardStage/title` | 0 / 226 | 760 / 44 | 204..248 |
| `notice` | 0 / 228 | 1080 / 32 | 212..244 |

两个文本框在横向和纵向都相交。选牌、跳过、领药、纯重绘、满槽选牌后、满槽拒绝和领取失金这七个状态有相同冲突；不是一条中文句子过长才发生。只缩短句子或把某个通知清空会留下同类入口。正确所有权由奖励列表/选牌分层实现负责，本附件只提供可执行守卫，不另改生产布局或交互。

## 为什么此前没有挡住

- `reward-potion-layout.test.mjs` 核对静态布局中的 skip/claimPotion/skipPotion/potionReward、卡牌运动包络和奖励标题，却没有把共享 `notice` 纳入；它没有在操作后读取实际文本与同时可见性。
- `looter_potion_ui.lua` 检查五按钮的外框间隔和安全区，认可了同排多动作布局；「按钮外框不互盖」不等于页面信息层级清楚，也不检查头部提示。独立药水事务的规则测试同样无法证明标题可读。
- `verify:ui` 是另一个实机证据门禁，核对候选哈希、批准稿文件、截图、审查者与关键检查项；它没有机器测量文字碰撞，也没有接进 `npm run check`。当前 `ui-acceptance.json` 的 rewards/cardChoice 都是 `partial`，其余页面也未全部 pass，因而**它没有通过，不能称作通过后漏检**。既有 `check` 通过与旧候选功能实测都不认证本轮奖励页面。

## 新的最小机器门禁

执行 `node --test tests/reward-readability.test.mjs`。测试自己构建数据/控件树并运行真实 Lua 宿主，约数秒，输出 `build/reward-readability.json`。现有 `npm test` 的 `tests/*.test.mjs` glob 自动收集它，Quality 的 `check:rules` 已包含 `npm test`，无需增加平行 CI 流程或改全局 AGENTS。单独改 Lua 时，`test:lua` 也会收集状态捕获夹具，但只有 JS 入口执行可读性断言。

23 个状态覆盖奖励列表、进入选牌/动画稳定/悬停、选后、跳过、领药、纯重绘、满槽及拒绝、失金领取；并抽查菜单、地图、营地、战斗及提示出现/清空。守卫检查：

- 渲染后的奖励标题、说明、反馈、动作 caption 与卡牌文字的文本框是否相交。
- 非空奖励文本框是否满足项目已证实的 `nativeText.lineHeight=40` 及声明的最小字号换行预算；明确换行不靠 autoSize 缩字掩盖。
- 列表/选牌是否互斥、列表是否有离开动作、选牌是否泄露领奖行/离开按钮、全局战斗提示是否给局部奖励提示让出所有权、已领取条目是否仍显示。
- 用来自真实生成树的标题作负控，强制把长提示或按钮 caption 放到相同框中，断言守卫拒绝；隐藏提示和同位背景图片保持合法。

几何读取优先采用实际 `SetAnchoredPosition`、`SetSizeDelta`、`SetLocalScale` 的结果，再回退生成树的初始属性，递归叠加父坐标、缩放和可见性。原生 presetButton 在宿主内部切换状态，夹具会保留四个分支，因此只读取本次 normal/disabled caption，避免把同一按钮的四个状态当成四段叠字。

这是语义组守卫，不是任意控件盒相交检查：背景、边框、图标、命中框、卡片内部及已批准的状态详情透明框重叠不触发。战斗单位名称和生命的透明 40 高框间距为 28，实际字行较小；它们只与全局反馈比较，不互相误报。奖励 UI 的文字盒层级采用明确分离的设计契约。

## 红例与相邻审计

[结构化红例](../evidence/reward-readability-red-b91a461.json) 保存了 23 状态名、七处真实文本/坐标冲突、38 个重复状态下的文本框预算问题、测试输出与捕获文件哈希。基线运行 5 项：3 项失败、2 项通过，退出码 1。失败分别为碰撞、原生行预算和新列表/选牌所有权。绿例须由奖励流程实现组合后执行，不能把本测试独立分支的红状态写成已修复。

相邻菜单/地图/营地/战斗的头部与反馈没有发现同类相交。地图与营地的反馈注入控制器字段，战斗反馈用夹具注入 notice，随后走真实 render；它们是几何抽查，不冒充玩家自然触发过这些反馈。

相邻风险另输出 `build/ui-readability-adjacent-risks.json`：地图 notice 高 28、战斗 notice 高 32，低于已知 40 高原生合同。地图图例也沿用 28 高源码框，未在本门禁角色组内。它们不是本轮新实机确证，也未以本次奖励修复代为验收，应在既有界面品质任务中对照候选实机复核；不为它们重复创建任务或扩大当前生产修改范围。菜单与营地抽查文本预算未发现问题。

本门禁不测原生字体笔画、真实裁切、屏幕安全区遮挡、触控命中或手机观感。新的组合候选仍须按 PLATFORM_PARITY 与 `verify:ui` 留实机截图及审查记录；测试绿不能更新 `ui-acceptance.json` 为 pass。
