# PR163 卡牌商品槽位修正

本次仅修复商店商品寻址，不改变 TASK-13.1 的认领、范围、状态或原版/平台验收结论。

## 原因与接口

Courier 补货允许同 ID 商品并存。固定 seed42、显式 Courier 和 10000 金币，通过 Map API 导航至商店并购买首槽六次后，前两槽分别为 anger / 37 与 anger / 42。旧 UI 只传卡牌 ID，核心取首个匹配，点击第二槽也会扣 37 并补第一槽。

- 新增 `Nodes.buyCardSlot(run, slot)`，校验 1–7 的整数槽位；后续资金检查、发牌、补货和扣款使用同一个选中商品。
- 旧 `buyCard(run, id)` 保留唯一匹配兼容；同 ID 多槽拒绝为 `item_unavailable`，不再首项兜底。
- UI 购买绑定当次 render、run/map、nodeFlow 和商品列表引用。补货或折扣事务替换列表后，旧回调与旧触摸不能购买新货；既有触摸归属和遮罩取消逻辑保留。
- 槽位 API 表示购买当前槽，不是可跨商店持久保存的报价 token。没有新增报价管理系统、禁重牌、改价格/RNG 或改变缺池策略。

## 验证

`tests/lua/shop_card_identity.lua` 自动纳入既有 Lua 测试发现，15 组覆盖真实第二槽扣 42、首槽扣 37、只替换所选槽、一个永久 UID、只够便宜槽时贵槽原子拒绝、所选槽坏补货流回滚、非法/缺失/不可售/售罄/离店拒绝、旧 ID 兼容与歧义拒绝，以及购买/外部补货/重绘/遮罩/新店/重开后的旧回调和触摸。

先在 ec94 原生产代码上得到 12 组红例、3 组控制通过，再作最小修正得到 15 组通过。运行基线组合 ec94 商店切片与 develop `3bd3afaf`；`ui_theme.json` 和 `validate-data.mjs` 使用共同基线 `7e1123b1` 三方合并，保留主线状态帮助与酸液 schema，不作额外改动。

本地 liblua5.4 执行全部 141 份 Lua 夹具通过，直接 Node 定向 120 项通过；JS 语法、数据验证及 data/UI/map/theme 生成通过。首次 native 执行未设 LUA_PATH 的 13 个加载失败已修正执行环境后完整重跑；一次 Node 主题加载检查因本地无 Fengari 报缺依赖，其余 123 项通过。未安装依赖、未运行完整 npm/Fengari CI，native 结果不代替最终 SHA 的正式 CI。没有构建游戏副本、官方导入或实机/UI 验收。
