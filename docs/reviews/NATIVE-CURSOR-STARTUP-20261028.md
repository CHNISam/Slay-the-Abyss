# 原生点击区字段错误漏检复盘

用户导入 `8770e9d4` 候选后，在启动页看到 `abyss_battle_ui:701: cannot set interactable, no such field`。本次候选不能启动，用户无法继续验收商店、宝箱和营地。之前的离线编译和源码/布局摘要一致均成立，但没有检测到这个原生能力错误，不能视作启动成功。

## 因果与责任

牌堆入口是 `cursorArea`，代码向它写入只属于预设按钮的 `interactable`。宿主构造时就会渲染战斗控件，因此没有进入战斗也会触发。

现有宿主 fixture 给所有类型的控件都预置 `interactable=true`，普通 Lua 表也允许任意新增字段。测试因此主动模拟了平台不存在的能力。工具链静态检查的字段列表是类型合并的，不能区分这个字段用在哪一种控件上。源码摘要审计证明的是打包内容一致，不检查运行时字段。交付时完整CI与官方启动仍缺失；虽然已标明候选未实机验收，仍把基础启动风险留给用户发现，这是本次工程验证没有做到位的地方。

## 修复和机械保护

1. 牌堆入口改用 `SetVisible` 表达可点击性；现有回调继续校验当前战斗、输入所有权与遮挡，旧回调不能越过状态限制。保留预设按钮合法的 `interactable`。
2. `tests/lua/support/native_ui_contract.lua` 为五套主要真实控件工厂增加 `cursorArea` 写字段限制。删除虚构的初始字段，拒绝写入true和false，不能靠已有字段绕过 `__newindex`。这只是本次已证实的能力边界，不宣称完整模拟客户端API。
3. `native-startup-contract.test.mjs` 对生成控件运行真实宿主构造与开始操作，再在内存中把本次错误语句精确注回同一生产构造流程。只有正常版本成功、错误版本明确死于该字段能力断言时才通过；不修改工作树，不把超时或其他异常当作成功拦截。
4. `ui_mock_contract.lua` 对五套工厂逐一验证：点击区拒绝两种布尔写入，仍可控制可见性；预设按钮可正常设置该字段。防止一刀切禁用字段破坏按钮。
5. 新命令 `npm run check:native-ui-contract` 已接入已有 `check:engineering`，CI现有工程作业自动执行。另有JS测试与Lua全量测试覆盖，不依赖口头提醒或人工记忆。

完整写序列从 `75180 / 1258450308` 改为 `75096 / 240481077`：移除84次虚构字段赋值；其余既定步骤和文字契约保留。当前CI另外暴露的手柄旧选牌路径、捕梦网测试忽略休息演出时间问题同步修正，仍保留拒绝重复操作与卡牌真实获得检查。
