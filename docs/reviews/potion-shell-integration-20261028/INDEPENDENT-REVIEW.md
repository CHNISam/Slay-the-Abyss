# Potion-shell fidelity review — 2026-10-28

## Decision / actionable findings

1. **Do not call phase4 source-equivalent.** Its filled shell has a genuine remaining mismatch: an inscribed, small highlight over the darkest source endpoint creates a local spotlight instead of the source's broad radial brown field. Main/Map source hashes agree with phase4's manifest. At native scale, source farthest-corner radius is about 28.429, while phase4's highlight radius is only 11.133. In the existing offline linear-soft-disc model, mean light contribution is 0.588 (source) versus 0.155 (phase4). The phase4 image visibly confirms this difference.
2. **Use the narrowly scoped fitted-shell proposal if the writer accepts its documented approximation.** `shell-fit-proposal.patch` changes only the helper and adds theme fields. It uses the existing solid disc + two existing soft discs, all geometrically bounded in the face; no new ID, renderer, clip API, runtime command or interaction. Compared with the existing offline semantic model, all-face RGB MAE falls from 8.808/10.252 (normal/fire) to 1.290/1.479. Worst channel error remains 4.601/7.335. This is a closer approximation, not pixel equality or native proof. Top and bottom source edges differ; the bounded approximation still has a constant-color extreme edge.
3. **The round bottle in `same-state-compare.png` is not evidence of the runtime bottle shape.** The preview maps all potion IDs to the pre-existing prototype `i-potion` glyph, while Lua uses `Theme.icon.potion[id]`. The design handoff explicitly requires existing official top-bar/potion assets and says custom SVGs are schematic. Do not invent a new ID or reimplement a flask merely to make an offline comparison look right. `shell-only-compare.svg/png` removes bottle proxies from every row and labels the remaining evidence correctly.
4. **Existing tests prove self-consistency, not the broad source gradient.** `tests/potion-shell-source.test.mjs` hard-locks the narrow highlight to 22–23 and base to `#221A17`. `check-render.py` only proves one light pixel exceeds one dark pixel by 8, plus empty alpha and dash gaps. Both pass the rejected spotlight. `potion-shell-fidelity-proposal.test.mjs` instead reads the actual Main/Map HTML source parameters, checks 7,837 face points and top/bottom/side/middle region errors, enforces no assumed clipping, and fails phase4 (2/2 RED) while passing the proposal (2/2 GREEN). Its 2/255 MAE and 8/255 pointwise bounds are provisional **offline engineering regression** ceilings, not user UI-acceptance criteria. Port this in place of the narrow-light/base hard locks; keep the alpha/dash/state assertions.
5. **Control cost is material.** Current helper has 35 controls, 30 images, versus old helper's 3 controls: +32 × 5 slots × 4 states = +640 per full five-slot entry. Of its 600 allocated images, 360 are dashed-empty rectangles; they are not 360 simultaneously visible images. The fit adds one image to each filled/fire shell = +40 allocated controls per entry, or +80 if the combined Game contains both battle and utility entries. Parent reports final integrated battle 2603→3243 (+640), max direct children 60, Game 10331; these are allocation/capacity counts, not phone performance evidence. This review directly confirmed helper arithmetic, not those moving integration-tree totals.
