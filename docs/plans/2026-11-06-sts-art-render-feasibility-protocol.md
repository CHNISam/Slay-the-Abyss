## 0. 唯一目标与固定事实

**产品目标**：在千星奇域实现视觉上接近《杀戮尖塔》的选角背景、主角及怪物轻待机、卡牌插画、出牌与攻击反馈；不以显著失真、不可接受的等待、卡顿或超额成本作为交换。

**不再重复验证**：平台不允许把任意自定义 PNG 直接作为一个普通客户端纹理导入。GIA 是图元/控件结构的载体，不是“任意 PNG 变成一个 GPU 纹理”。若今后出现新的官方能力，必须保留接口文档及真实导入证据后另行重开该路径，不能靠猜想取代当前研究。

**已有证据，均不可外推**：
- 2026-10-30 同候选 V9 约 4,500 图元背景 Ready 10s、选角主图 Ready 6s、头像 Ready 7s；这些不是安卓 FPS，也不是新候选数据。来源 docs/plans/2026-10-30-art-loading-performance.md。
- 现有 144x64 三张卡片 compact 同源基线：strike/defend/bash 分别 918/835/916 个矩形，PSNR 19.93/20.95/20.65dB，实际对照明显失细节；不存在“同画质优化成功”的结论。来源 experiments/art-tech-lab/baseline-audit/README.md。
- 既有原始资源：13,201 背景矩形、4,822 头像图元、4,315 战斗形象图元；另有 4,500 背景预算版与选角低多边形候选。资源是否启用由候选 receipt 决定，不能以入库冒充真实加载。
- 正式关卡容量旧面板曾读到 8.96MB/20MB，属于历史候选；新构建仍 UNVERIFIED，参见 docs/PLATFORM_LOAD.md。

**四项被分别检验的成本**：数据读取/解码 D、原生对象创建 I、首次呈现 R、每帧显示/更新 F。另单测常驻内存 M、包体 S 和内容制作成本 A。**图元数不是唯一自变量**：总对象、可见对象、更新对象、新建对象、图元类型、重叠、深度、缓存驻留要分别计数。

## 1. 判定模型：先建立可行域，不预先选择算法

对每个候选 c、目标设备 d 和完整场景 s，建立记录：

- 画质 Q(c,s)：真实显示尺寸下的盲审通过/不通过，附原图同画面截图和客观误差；先通过 Q，才比较性能，不允许用更糊的图冒充提速。
- 冷进入 T_cold(c,d,s)：从同一可操作起点触发，到**画面完整且交互真实可用**；须同时记录应用/关卡启动与菜单页面等待，防止把等待搬到更早时刻。
- 暖切换 T_warm：已经进入并退出过同一界面后的再次完整可操作时延；规定缓存状态并测重复进出，不能与冷样本混算。
- 稳态帧时间 F50/F95/F99、>100ms 长帧次数、输入响应 P95、对象/内存峰值与 30min 后残留。统计须注明真实观测入口（官方动态检测/系统帧时间/高速录像）；Lua OnUpdate dt、模拟器 RPC、Lua setter 次数均不能充当 GPU 帧时间。
- 开发者容量：官方关卡/服务器读数、图元与宿主数、生成时间、手动精修时间；数据文件字节不等于官方包体或 RAM。

目标门槛（**实验前声明的产品目标，不是平台硬上限/已验事实**）：
- 同源画质通过 Owner 盲审：148x208 卡面及 144x64 插图区、选角真实人物显示尺寸；关键头脸、武器、色彩、轮廓、透明边缘不得出现可感知的大块马赛克/接缝。自动 MAE/PSNR/SSIM 和头脸局部误差只作解释性证据，不单独授予视觉 PASS。
- 完整可操作首次进入目标 ≤1,000ms，缓存切换目标 ≤100ms；超过目标为 NOT MET，不能改起点或隐瞒启动预热。持续 30 FPS 档：真实帧时间 P95 ≤33.3ms，P99 与长帧次数必须报告；60 FPS 档目标 P95 ≤16.7ms。对关键交互不得出现明显阻塞；单靠 P95 不构成完整 PASS。
- 关卡面板不得超过官方 20MB、服务器不得超过 3MB；16MB 为项目内部预警；正式证据按 docs/PLATFORM_LOAD.md。未知内存/帧时间必须标 UNVERIFIED，不得判 PASS。
- 预算不按“每卡 2,000 图元”一维决定；仅当 Q、T、F、M、S、A 与完整场景均可接受时，才得到该候选的条件 GO。其他约束没测齐时只能标 PROVISIONAL。

**退出纪律**：若基础场景本身不达标，先定位基础 UI；若方案失去同等画质，停止性能排名；若两个技术只在单图成功，不能批准 75 卡量产；若平台不提供某项可测数据，以 UNVERIFIED + 原始现象/替代测量方案报告，绝不补一个估算数冒充官方。

## 2. 实验次序和每步可得结论

### P0 — 测量可信性与基线冻结（前置硬门，不能跳过）

**问题**：我们是否能区分“源码创建完”“画面全显示”“玩家能操作”？

1. 记录当前 develop SHA、干净的隔离工作树、工具及编译版本、实际输入图片 SHA256、基础 GIL SHA256、设备型号/OS/刷新率/千星版本/画质档位、构建 receipt 和实验 ID。
2. 录制统一可见触发事件：用户操作触发时出现标记；最终一块图元出现后显示另一个标记；执行真实点击并收到确认时为可操作终点。计时点对齐实际画面录像/官方事件日志，不以内部 ready 标志自证可见。
3. 计数器分别覆盖新建/释放对象、当前可见、当前更新、容器数、静态控件数、Lua Setter 数、失败重试与异常；校准 0 控件与 1 控件探针。对没有 API 的“引擎内部 DrawCall/GPU 耗时/真实对象数”明确标不可直接测。
4. 每组至少 3 次独立运行，正式比较使用 A-B-B-A 或等价交错顺序，防止热机、缓存、首测效应。冷启动须清楚定义游戏进程/关卡/缓存是否重置；如果无法确保真正冷载，就把该数据标为“进程重开”而非冷载。正式稳态每轮 60 秒，丢弃预热前 10 秒，并记录实际样本帧数。各组不得在运行中改变窗口尺寸/画质/帧率锁。

**PASS**：同一触发路径、同一候选内容，日志、录像、源身份可完整互相核验；注入“只显示一半”“失去点击”“无性能来源”的负控会被报告判失败。否则不能继续比较算法。

### P1 — 容量/更新成本曲线：先探性能上限，不先画新图

**假设 H1a**：大量已创建但隐藏的控件本身也造成常驻开销。
**H1b**：可见静态图元的成本与更新图元的成本不同。
**H1c**：修改一个父容器与修改其所有子图元，原生写入成本和实际帧时间不同。

**实验夹具**：专用隔离 UI 容器、一个固定 1280x720 画布、同一官方矩形图元模板；背景一致，随机种子固定，所有图元在同一固定区域排布，新增图元时按同一序列增加细分但不扩大覆盖区域，不允许增图元同时增加亮度/可见面积/动画复杂度。每组额外记录父子深度、总不透明覆盖面积和像素重叠倍数，避免把填充率与 N 混淆。

**首轮自变量**：N=0/1,000/4,000/8,000；每 N 下四状态：隐藏并驻留 H，完全可见且静止 V，可见且只改变统一父容器位姿 P，可见且逐子调用位置 Setter U。首次创建计时作为独立阶段 C，不混入稳态。确定转折点后以 500/2,000/16,000 等邻档或二分法补点；若设备温度、错误或渲染时延已超出门槛，停止向更高档推进。每状态 3 次 × 60 秒。

**差量**：V−H 指向可见路径额外成本；P−V 指向整体变换；U−P 指向子控件原生更新；H−N0 指向驻留成本。仅为同设备统计关联，不能从这些差量直接推断具体 GPU DrawCall 或引擎算法。

**二轮交互实验（只在首轮发现负担后实施）**：固定 N 与同一颜色/覆盖，分别单独改变矩形/三角/椭圆种类、完全不透明/半透明、大量重叠/尽量无重叠、浅/深容器树，以 2×2 交叉试验复核是否为图元数量之外的限制。矩阵不可把图元数、面积和透明度一次同时改掉。

**交付**：每类状态的 N→P50/P95/P99 帧时间、长帧、内存曲线，首次创建墙钟与失败点，以及**在目标游戏剩余预算下**可行的成本域；不得发布一个通用“手机最多 X 图元”数字。若 N=0 基础 UI 已超门槛，转向 TASK-4.21/既有 M7 运行时证据，而非继续图元拟合。

### P2 — 冷加载归因：仅用同一份 4,500 图元背景

**假设 H2**：Lua 逐图元动态 Instantiate 是主要玩家等待来源；预制或缓存可降低**总**等待，而不只是把它移到进入游戏前。

同一 480x270 既有 background-budget-v1 数据，同一 4,500 图元、RGBA、坐标、层序、容器/裁剪结果；同显示画布，必须对照渲染结果。三条候选：
- A：当前 Lua 动态创建（原基线路径）。
- B：如平台支持，直接在 GIA/UI 层级预置相同子控件，仅切换页面显示；明确其加载发生在哪个阶段。
- C：如平台支持，事先保存同一树为客户端模板并运行时一次 Instantiate 模板（但须记录模板展开后的真实控件数，不得把“一次 API”叫“一对象”）。
- D（成本归因对照）：完全相同 A，仅提前创建并缓存一次；用于检验是否只是费用前移/内存换等待。

**测量**：启动到主菜单可操作、菜单到背景完整且可点、启动到首次完整可操作的端到端总时间、第二次进入、创建/释放/峰值驻留、完整截图、包体/内存。冷测每组 5 次、暖切 10 次、顺序交错；至少 3 次是最低可解释基线，不能以一次偶然快宣称路线胜出。记录同版 PC 与安卓分开，不合并跨设备统计。

**决策**：
- 若 B/C 明显降低进入时间，**但启动到首次完整可操作不改善**，只判“等待转移”，不得 GO；
- 若 B/C 总时间改善且 Q/F/M/S 均可接受，优先预制路线，停止不必要的 Lua 层微优化；
- 若 B/C 根本不受平台支持，标 NOT SUPPORTED，跳过而非造假；若全部相近，创建方式不是唯一主因，回 P1 的实际成本曲线/原生初始化归因；
- 若 D 的暖切快但内存/初始化恶化，保留具体取舍，禁止默认“缓存一切”。

### P3 — 同源画质成本前沿：只在 P1/P2 知道可承受域后执行

**假设 H3**：混合图元或定向视觉精修，在**相同真实画质**下可以显著降低实际成本，而不只是在降低原图分辨率。

三类素材逐项固定源 SHA、尺寸和显示大小：背景（已获视觉认可的原图及 4,500/13,201 旧候选）、荧角色（获认可的战斗形象与当前低多边形候选分别保留）、三张现有卡 strike/defend/bash（144x64 真实插图区；源图若是小缩略图，记录输入信息已损失，不能将其当高分辨率原画）。先选同一资产同源比较；不得“替换为别的官方图标”后宣称同画质减少成本。

候选 E=现有矩形基线；F=合法使用的混合矩形/椭圆/三角图元（例如 Interverse 的 MIT 实现，单独核对其依赖和输出条款）；G=同样图元预算下的重点局部精修/分层设计。对于每个候选以 N=400/800/1,600/3,200 起步，再按画质和 P1 容量补档。算法生成用时是开发成本 A，不是玩家加载时间。

画质在真实尺寸下盲审，并提供原图及输出原生截图、全图 MAE/PSNR/SSIM、头脸/发丝/武器/透明边缘单独局部指标。盲审先不告诉算法/图元数；不允许用降画质或隐藏关键细节通过性能门槛。先找每种方案最小**视觉通过**成本集合，再把通过项送 P1/P2 的真实负载环境。

**可能结果**：F/G 同质量更少且更快→保留；同数更好但仍超负担→研究表达/画质设计而非声称性能突破；全部超可行域→停止在纯图元拟合上无限迭代，改走官方原生资源、从设计阶段可原生表达的图形构图等路线，并重新做同画质审查。不得把“压缩率”当 GO。

### P4 — 组合交互与长期运行：将局部成功转为产品判断

固定同一游戏源码、起始 seed、敌人/卡牌/状态、操作脚本、视角、画质和客户端版本，递增五个场景：
- L0 当前正式可玩基线：无实验精绘（记录默认 UI 与系统负担）；
- L1 选角背景＋荧肖像＋人物轻待机；
- L2 战斗背景＋主角＋3 个敌人（现有待机）＋1 张卡；
- L3 L2＋5 张精绘卡，按预定操作脚本连续 20 次出牌/回退；
- L4 L2＋10 张精绘卡＋多段攻击、增益/减益与粒子并发，接着 30min 连续重复进出页面。

单独保留“静止无特效”和“高峰有特效”的同一场景差量，完整统计冷/暖时延、真帧、输入延迟、对象与内存峰值、释放后残留和官方负载（静态/动态）。禁止用 L1 或单张卡 PASS 批准 L4 或扩产全部 75 张卡。

**通过后才考虑生产接入**：小范围最优候选切片与现有截图/语义回归，当前 M7/M8 Sprint 准入、独立复审、Full/原生 Queue/合后 Full、官方同候选 RC 证据均不可省略。实验成功不修改发行侧 cards=false 决策。

## 3. 统一报告合同：每一步都有可复现的裁决

每次试验生成以下文件/字段（可复用既有工具与报告，不另建长期服务）：
1. manifest：experimentId、phase、hypothesis、sourceCommit、sourceDirty、asset SHA256、builder/engine/client version、GIL/receipt/candidateSha256、device model/OS/refresh/quality、测试者与时间。
2. conditions：唯一改变的因子、固定条件、随机种子、N_total/N_visible/N_updated/N_new、几何类型/透明/overdraw/depth、cacheState、launchMode、触发动作及明确时间点。
3. raw：按 runId 保存每次时长、时间戳、有效帧数、P50/P95/P99（样本过少则不算）、长帧计数、Lua 调用、对象创建/释放、官方容量/内存以及证据来源；失效/失败样本不得删除。缺测字段用 null + UNVERIFIED。
4. visual：有权限的原图 hash、同尺寸对照、实际客户端截图/录像、盲审记录及不合格部位；涉及私有游戏截图/UID 时保留私下证据或脱敏。
5. verdict：PASS/FAIL/UNVERIFIED/NOT_SUPPORTED，具体到每条假设；不把加载快等同 GPU 快；缺任一最终产品维度不能 GO；给出 nextPhase、nextExperimentId、owner、最小改变范围和不可突破/仍未知项。

结果表（每一行对应一个可证伪结论）：

| 条件 | 可支持的结论 | 不可据此得出 | 下一动作 |
| --- | --- | --- | --- |
| P1 可见 N 增长而 F 恶化 | 该设备/覆盖/图元类型存在可见工作扩展成本 | 千星统一硬上限、GPU draw call 数 | 固定 N 检验类型/重叠/深度 |
| P1 静止正常、逐子更新恶化 | 更新路径有附加成本 | 所有动画方案都慢 | 试父容器/更少参数 |
| P2 预制明显降低端到端冷时间 | 该候选预制有效 | 图元变为单纹理、全场景必然快 | 进入 P3/P4 |
| P2 页面快但总启动未快 | 成本转移 | 加载问题已解决 | 重测启动/缓存取舍 |
| P3 盲审不通过 | 无有效同画质候选 | “少图元即可量产” | 调整表达，不评性能胜出 |
| P4 组合不达标 | 单点结果不能外推完整游戏 | 全部路线不可能 | 用场景差分定位后重新 P1/P2 |

## 4. 执行顺序、产物与严禁事项

1. **PR-A / 当前协议（本次）**：只更新本计划，不改任务、运行时、美术数据、CI 或正式构建；人工核对现有路径/条件，文档评审与 Required CI 后再合入。状态仍 NOT EXECUTED。
