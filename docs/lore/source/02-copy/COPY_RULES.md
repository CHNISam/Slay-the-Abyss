# 文案使用规则

**唯一文案源**：`narrative.zh-CN.json`。切勿把这份包里的 JSON 当成项目已识别的运行时 schema：Agent 可按仓库既有构建方式决定如何取值/生成。

## 字段与状态

- `flow.intro / bossEntrance / victory / defeat`：`approved_draft`，主文案直接沿用用户认可的前一版原句。
- `full`：原句、长版；`compact`：为了界面空间而追加的短版提案，不是原文。
- `nodeFlavor` 与 `specificEvents`：`candidate`，辅助风味文本，**可全部延后**。
- `displayHint`：建议接入位置，不证明宿主已具备文本窗口。

## 落地优先级

1. 主菜单的短背景：明确为何进入遗迹，但**保留操作说明与「启程」按钮**。
2. 结局一行：胜利和失败分支分别渲染；**原有统计、重新启程、正式结算**不变。
3. Boss 登场：如有低风险提示位就接一行短版，没有就只保留资产文案，**不新造弹窗**。
4. 节点风味文本：按现有场景和事件准确性择优接入；与既有事件信息冲突则不接。

## UI 尺寸不够的处理

`full` → `compact` → 本轮仅保留在文案资产中。严禁通过覆盖战斗 HP/费用/意图、删掉结算数据、在移动端缩到不可读字号等方式硬塞剧情。

不要为了这几句话创建额外语言选择、剧情编排、对话树、NPC、CG 或新随机事件。原作设定真实性见 `../01-world/CANON_BOUNDARIES.md`。
