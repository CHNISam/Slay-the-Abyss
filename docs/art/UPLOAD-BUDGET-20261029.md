# 试玩上传存档大小与精绘图元：10/29技术门槛

2026-10-30 后续确认：用户官方编辑器截图基线为关卡8.96MB/20MB、服务器0.01MB/3MB，静态计算/内存正常。下文“20MB未确认”保留10/29研究时态；数值基线与现行双层工程门禁见 [平台负载](../PLATFORM_LOAD.md)。截图尚未绑定本轮新候选，不能冒充优化后的容量或动态/手机验收。

## 已确认是什么，尚未确认什么

用户明确路径是“导入关卡存档→进入存档→点击试玩→上传”，本次约10MB，上限记为20MB。调查对象是**关卡存档/试玩上传数据**，不是原神安装包、Git/LFS容量，也不是玩家退出续玩的局内存档数据，更不是自定义小地图图片配额。

官方《负载计算功能》把“存档大小”定义为关卡保存后上传所需存储空间的预估，超上限会禁止上传；《试玩》说明试玩经过校验与上传。已确认指标类别与用户流程吻合。官方客户端脚本说明还明确：只有建立映射的Lua文件才会打包上传，本地任意文件不会自动上传。

**20MB数值、十进制/二进制单位、压缩前后口径、外部映射Lua是否并入同一读数，本轮未获得官方数值条款或实际上传面板证据。** 暂按用户观察的20MB做保守工作上限，不冒充已核定技术常量。本轮没有拿到那次候选GIL与完整上传窗口，不能给它的10MB成分占比，也不能声称还恰好剩10MB可塞图片。上一轮把小地图20MB配额列为答案依据不适用，撤回该对应关系。

## 当前项目究竟把什么写入候选

审查固定 `20a74da73ff5379a748e6b9687b258e2c9a22bf8` 的 [build-native-candidate.mjs](https://github.com/CHNISam/Slay-the-Abyss/blob/20a74da73ff5379a748e6b9687b258e2c9a22bf8/scripts/build-native-candidate.mjs)：

1. 读取基础GIL，生成运行时data/theme/presentation/map/narrative，枚举全部`src/lua/*.lua`及生成模块，通过scene_set_client_script写入候选。
2. 将生成UI布局和模板写入GIL；启用精绘时，动态绘图资料进入presentation，宿主绘图控件池进入布局。默认不传nativeCardArt选项不会自动开启精绘。
3. 构建器已有旧abyss脚本清单清理、所有权检查、模块摘要读回；必须保留。sourceInputs是来源摘要清单，不等于把全部scripts/tests/art源PNG上传。

因此，原始PNG压小并不必然减少原生图元绘制表；几千个原生形状/控件虽然不携带原始PNG，也会产生几何、颜色、层级、模板和脚本数据。官方内置图片按素材ID引用的路线，与外部PNG压缩路线不是同一成本模型。引用仍有配置成本，不能说完全不占包体或内存。

## 已知样本成本：只用于估算，不冒充上传增量

现有旅行者精绘登记见[源资产说明](../../art/cards/traveler-geo/README.md)。以下为仓库原生文件字节和图形数，不含卡框/动态文字/宿主/整屏其它控件。

| 样本 | 图形数量 | native-art.lua字节 | native-art.json字节 |
|---|---:|---:|---:|
| 整备武装 | 1834 | 350789 | 1214781 |
| 星陨剑 | 2657 | 481737 | 1748513 |
| 重剑斩 | 2043 | 368509 | 1343390 |
| 合计 | 6534 | 1201035 | 4306684 |

JSON和Lua是同一绘图的不同表示，不能相加当作必须上传5.5MB。最终装配会生成另一份运行时格式；平台还可能编码/压缩，必须实测。旧源图/LFS体积也不等于这个表。

当前实验按最大2657图形加45组与1根，为每个卡位预分配2703控件；1/5/10卡位分别增加2703/13515/27030，包含隐藏预分配。**唯一插画数量**与**同时显示的卡位数**是两个维度：同张图出10张手牌可以共享绘图数据，但仍可能有10份控件实例；反过来100张不同图只有5张同屏，绘图数据仍可能全部打包。不能把10卡池控件数乘全卡池张数，也不能只看同时5张就忽略全部唯一图的数据。

方向性结论：精绘可用性未被否决，但“当前约10MB，所以还能放心把所有卡/角色批量装进去”没有证据。三张Lua原始绘图约1.20MB已说明必须先做去重/装配预算；10卡27030新增控件也使运行期容量成为独立风险。禁止仅凭这些源码数字宣布一定超20MB，或宣称压缩必然能解决。

## 一个实验同时回答包体和美术路线

复用TASK10.1.2及现有原生装配脚本，不新增大框架。所有实验用同一干净底图、同一提交、同一客户端版本，输出独立目录；不覆盖用户正在测的存档，不改变规则/音频/结算图。

| 候选 | 只改变的变量 | 要回答的问题 |
|---|---|---|
| B0 | 当前正式可玩候选，不新增精绘 | GIL/映射Lua/平台存档大小/上传读数的基线关系 |
| B1 | 一个已批准精绘样本、一个宿主 | 唯一图数据与单宿主新增控件合计增量；是否能正确显示/操作 |
| B1b | 同一宿主池再注册另一张不同样本，交替显示 | 保持池尺寸不变时每张唯一图的实际新增数据 |
| B5/B10 | 仅在B1通过后扩至5/10宿主，同一份图数据 | 宿主池成本、是否重复嵌入同一绘图、手机峰值 |
| BM | 通过前档后才组合角色/合法最多敌人/背景/奖励覆盖层 | 真正成品场景容量，不能用孤立卡牌批准全游戏 |

每行记录：sourceSHA、baseSHA256、GIL字节/hash、实际映射脚本总字节与数量、生成presentation字节、唯一绘图digest数、模板/实例/可见/隐藏控件数、**静态负载“存档大小”及上限截图**、**试玩上传总量及单位截图**、客户端版本/设备；若平台只给进度而不公开编码口径，就如实记录未知，不能把GIL字节强行当上传值。排除网络重传累计字节与单次逻辑包体混淆。

手机同设置比较加载、交互和连续30分钟资源清理；观察真实帧时/设备负载或可复核录像。脚本OnUpdate间隔不是GPU FPS。重复进出后控件数量/内存不应持续增长，隐藏不等于销毁。

可用于规划的模型是 `实际上传 = 基线 + 唯一绘图数据 + 布局/模板/实例序列化 + 其他新增项 - 被真正消除的重复项`。分别测B1b和B5才能拟合，不凭JPG压缩率外推。建议内部门禁保留至少20%确认上限作为迭代余量，这是工程提案不是平台规则；数值上限未证前先以用户20MB保守估算、不得据此放行量产。

## 如何优化而不牺牲批准画质

先检查同一图被presentation/模板/多个宿主重复写入、旧模块/模板残留、隐藏预分配以及无关开发素材误入生产。复用已有共享CardDisplay、稳定图形digest、模板/实例池。生产资源按明确依赖清单裁剪需要单独证明无缺模块，Alpha/Dev完整研发源不删；不要盲目删除全src Lua或把来源摘要清单当打包清单。

优先评估原生模板复用/动态创建与实际可见宿主池；其省序列化能力必须由平台数据证明，运行时创建也不是免费。保留3D/2D混合、官方原生素材等既有可行候选，但不得未经用户审批把认可的精绘换成低图元占位或擅定每张200图元。若仍超预算，提交同构图A/B的实际增量、画质与手机体验，再决定局部路线，而非一次推翻全美术。

**GO条件**：计量口径清楚，B0/B1增量取得，成品组合在确认上限和内部余量内，实际手机性能/触控/清理通过。任何一项缺失即“未批准扩大装配”，不等于技术被判死刑。本轮所有平台测量均未执行；不能把本研究PR合并当作容量验收通过。
